## 2. 프로젝트 개요

### 2-1. 프로젝트명

**우심운까: 공공데이터 기반 운동 장소 추천 및 운동 습관 기록 서비스**

### 2-2. 프로젝트 소개 — "여러분의 미니홈피는 어떤 모습이었나요?"

우심운까는 **싸이월드의 미니룸과 친구 방문**에서 착안한 운동 서비스입니다.
할 일이 없어도 자꾸 들어가 보고 싶었던 '나만의 공간'의 재미를 **운동**과 연결했습니다.

- 사용자는 자신의 **운동 지역과 선호 운동**을 설정하고, **날씨·대기질·거리·운영정보**를 반영한 운동 장소를 추천받습니다.
- 운동 후에는 **칼로리를 기록**하고, 누적 운동량에 따라 **레벨업과 운동방 아이템 보상**을 받습니다.
- **친구 운동방 방문**과 **AI 운동 코치 '우심이'** 를 통해 운동을 계속 이어갈 수 있습니다.

| 🏠 나만의 운동방 | 🏃 오늘의 운동 장소 추천 | 🎁 운동 기록과 보상 | 👋 친구 방문 | 🤖 AI 코치 우심이 |
|---|---|---|---|---|
| 캐릭터와 가구를 드래그해 꾸미는 미니룸 | 지역·종목·이동시간 + 날씨·미세먼지로 오늘 갈 곳 추천 | 칼로리를 기록하면 레벨이 오르고 소품·스킨이 열림 | 친구 코드로 친구를 맺고 친구 방에 한마디 | 내 기록과 추천 결과를 바탕으로 운동 상담 |

```text
프로필 설정
→ 운동 장소 추천
→ 추천 점수·환경정보 확인
→ 운동 기록
→ 레벨업·운동방 꾸미기
→ 친구 방문·AI 코치 활용
```

> **다시 찾아오고 싶은 공간을 만들고 싶었습니다.**

![싸이월드 미니룸처럼, 다시 들어오고 싶은 운동 공간](docs/images/slides/01-intro.png)

### 2-3. 프로젝트 필요성(배경) — "그런데 운동하려고 하면 이런 생각이 들죠."

<div align="center">

**"오늘 비 오는데?"**   **"미세먼지 심하다던데?"**   **"근처에 어디로 가야 할지 모르겠는데?"**

</div>

운동을 시작하려고 하면 주변 시설, 날씨, 대기질, 이동시간, 운영 여부를 **각각 다른 앱에서 따로** 확인해야 합니다.
사용자가 운동을 미루는 대표적인 이유와, 이를 해결하기 위해 우리가 연결한 데이터는 다음과 같습니다.

| 운동을 미루는 이유 | 필요한 데이터 | 출처 | 서비스에서 하는 일 |
|---|---|---|---|
| 오늘 비가 오는지 알기 어려움 | 강수·기온·습도·풍속 | 기상청 초단기실황 | 실내·실외 시설 점수 조정 |
| 미세먼지가 심한지 알기 어려움 | PM10 · PM2.5 | 에어코리아 | 대기질이 나쁘면 실내 시설에 가점 |
| 주변에 어떤 시설이 있는지 모름 | 시설명·유형·주소·좌표 | 전국체육시설 API, 카카오 로컬 | 가까운 시설 후보 추천 |
| 이동시간이 얼마나 걸리는지 모름 | 거리, 사용자가 정한 최대 이동시간 | 좌표 계산 + 사용자 입력 | 이동시간 초과 시설 제외 |
| 시설이 운영 중인지 알기 어려움 | 공개 운영·휴무 안내 | 시설 공개 홈페이지 (크롤링) | 휴무 공지 확인, 감점 |
| 기록·보상이 없어 지속하기 어려움 | 운동 칼로리 기록 | 사용자 입력 | 레벨업, 운동방 보상, 친구 교류 |

> ⏱️ **이동시간 계산 방식** — 이동시간은 별도의 공공데이터가 아닙니다. 현재는 `거리(km) × 20분`의 도보 기준 추정치로, 실제 길찾기 시간과는 다를 수 있습니다.

![운동을 미루는 이유 = 우리가 모은 데이터](docs/images/slides/03-data.png)

따라서 시설 위치뿐 아니라 **환경정보와 운영정보를 함께 수집**하고, 추천 결과에 반영했습니다.
또한 이 정보들은 출처마다 형식이 다르고 계속 바뀌기 때문에, 사람이 손으로 모으지 않도록 **원본 보존 → 정제 → 품질검증 → 적재**를 반복하는 **데이터 파이프라인**을 함께 만들었습니다.

### 2-4. 공공데이터 활용 필요성

운동 장소를 제대로 추천하려면 "시설이 어디 있는지"뿐 아니라 "지금 가도 괜찮은지"를 알아야 합니다.
이 정보는 한 곳에 모여 있지 않아 **여러 공공데이터를 하나로 연결**해야 했습니다.

> **표 읽는 법** — ✅ 추천 결과에 직접 사용 · 🛡️ 추천 상세의 안전정보로 사용 · 🤖 AI 운동 코치가 조건 검색에 사용 · 🗂️ 수집·정제·적재 완료(현재 서비스 직접 조회는 제한적) · 🚫 현재 서비스에서 사용하지 않음

### 2-5. 프로젝트 목표 — "내 방을 꾸미듯, 내 운동 습관도 키울 수 없을까?"

**목표: 운동을 시작할 때의 망설임은 줄이고, 운동을 이어 갈 재미를 만들어 꾸준한 운동을 돕는다.**

| 목표 | 구현 내용 |
|---|---|
| 프로필 기반 추천 | 프로필에 저장된 지역과 선호 운동을 기준으로 장소 추천 |
| 환경 반영 점수 | 거리·날씨·대기질을 반영한 추천 점수와 추천 이유 제공 |
| 헛걸음 방지 | 추천 시점에 운영·휴무 정보 확인 |
| 믿을 수 있는 데이터 | 공공데이터와 문화빅데이터 수집·정제·품질검증 |
| 데이터 관리 | Supabase 데이터베이스에서 원본(RAW)·정제(PROCESSED) 데이터 분리 |
| 지속의 재미 | 운동 칼로리 기록과 레벨업, 운동방 꾸미기와 친구 방문 |
| 대화형 도움 | AI 운동 코치 '우심이' 제공 |

> **운동을 시작할 때의 망설임을 줄이고, 이어갈 재미를 제공합니다.**

> 데이터베이스 서비스는 **Supabase**를 사용합니다. Supabase의 관리형 **PostgreSQL**이 데이터를 저장하고, **PostGIS**는 위치·거리 계산에 사용하는 PostgreSQL 확장입니다. 문서의 PostgreSQL 표기는 DB 서비스 제공자가 아니라 기반 엔진을 뜻합니다.

| 구분 | 기술 | 사용 목적 | 🙋 쉽게 말하면 |
|---|---|---|---|
| Frontend | HTML, CSS, JavaScript, Django Template | 운동방·추천·프로필·친구 화면 | 사용자가 **눈으로 보고 누르는 화면** |
| Backend | Python, Django | 회원·추천·운동 기록·친구 API | 화면 뒤에서 **요청을 받아 계산하고 저장하는 두뇌** |
| Database | **Supabase** (관리형 PostgreSQL, PostGIS 확장) | 회원·시설·위치·운동 데이터 | Supabase는 관리형 **창고 서비스**, PostgreSQL은 저장 엔진, PostGIS는 "여기서 몇 km?"를 계산하는 **지도 기능** |
| Data Collection | requests, BeautifulSoup4 | API 및 운영정보 수집 | 공공데이터를 **받아 오고**, 홈페이지 글자를 **읽어 오는** 도구 |
| Coordinate | pyproj, Supabase PostgreSQL의 PostGIS | 좌표 변환 및 거리 계산 | 서로 다른 좌표 형식을 **하나로 맞추고**, DB에서 위치 간 거리를 계산하는 도구 |
| AI | OpenAI API | AI 운동 코치 | '우심이'의 **대화 능력** |
| External API | 기상청·에어코리아·카카오 | 날씨·대기질·주소·장소 검색 | 다른 기관이 제공하는 **정보 창구** |
| Deployment | Gunicorn, WhiteNoise, Render | 서비스 배포 | 누구나 인터넷으로 접속할 수 있게 **서버에 올리는** 도구 |
| Collaboration | GitHub, Notion, Discord | 협업·문서·알림 | 코드 공유 · 문서 정리 · 팀 대화 |

> 💡 **추천 로직은 학습 모델이 아닌 규칙 기반 점수 계산 방식입니다.**
> "AI가 알아서 골라준다"가 아니라, 팀이 정한 기준(거리·날씨·미세먼지)에 따라 **점수를 더하고 빼서** 순위를 매깁니다. 그래서 왜 이 시설이 1등인지 **이유를 항상 설명할 수 있습니다.**

### 시스템 구조 — 한 번의 추천 요청은 이렇게 흘러갑니다

![우심운까 시스템 아키텍처](docs/images/architecture.png)

> 아키텍처 그림의 `PostgreSQL + PostGIS`는 **Supabase가 제공하는 데이터베이스 엔진과 확장 기능**을 가리킵니다. 별도의 PostgreSQL 호스팅 서비스를 사용한다는 뜻은 아닙니다.

![우심운까를 만드는 기술](docs/images/tech-stack.png)

> 정기 파이프라인은 원본과 정제 데이터를 분리해 적재합니다. 추천 요청은 정제 데이터와 규칙 기반 점수를 사용하고, 운영 공지는 요청 시 크롤링합니다. AI 코치는 질문 의도에 따라 운동처방 테이블에서 일부 근거를 조회해 답변을 생성하며 대량 원본 전체를 AI에 전달하지 않습니다.

## 6. ERD

> **ERD(Entity Relationship Diagram)** — 데이터베이스에 어떤 표(테이블)가 있고, 표끼리 어떻게 연결되는지 그린 그림입니다.
> 예를 들어 "회원 1명은 운동기록 1개를 가진다", "회원 1명은 친구를 여러 명 가질 수 있다" 같은 관계를 나타냅니다.

### 6-1. 주요 테이블

| 테이블 | 쉽게 말하면 | 주요 정보 |
|---|---|---|
| `Member` | 회원 카드 | 이름·닉네임·비밀번호 해시·주소·**친구 코드(USIM-XXXXXX)**·방 꾸미기 상태 |
| `WorkoutProgress` | 운동 통장 | 누적 칼로리, 최근 운동 기록(최대 30건) → 레벨 자동 계산 |

| `Profile` | 추천용 프로필 | 닉네임·연령대·도시 (기존 추천 기능 호환) |

### 6-3. 추천에 쓰이는 데이터 테이블

운영 데이터베이스 서비스는 **Supabase**이며, 저장 엔진은 PostgreSQL입니다. Supabase PostgreSQL의 별도 스키마에서 수집 원본은 `m3_raw`, 정제 데이터는 `m3_processed`, 파생 결과는 `m3_derived`, 실행 이력은 `m3_monitoring`에 저장합니다. 추천·AI 코치는 정제 테이블을 조회하고, 원본 데이터는 재처리와 장애 분석을 위해 보존합니다.

**운동 장소 추천**

- `m3_processed.facility` — 시설명·유형·지역·주소·좌표로 후보를 조회하고, 지역·운동 종목을 필터링해 거리 점수를 계산합니다.
- `m3_processed.weather_ultra_ncst` — 격자(nx, ny)와 기온(T1H)·습도(REH)·강수(PTY·RN1)·풍속(WSD)를 이용해 실내·실외 추천 점수를 보정합니다.
- `m3_processed.air_quality` — 측정소의 PM10·PM2.5·오존·통합대기지수로 대기질 점수를 보정합니다.

**추천 상세 안전정보**

- `m3_processed.aed` — 설치 주소와 상세 위치를 추천 상세 화면에 표시합니다.
- `m3_processed.culture_sports_facility_safety_inspections` — 시설의 안전점검 결과와 점검일을 표시합니다.
- `m3_processed.public_open_facility` — 공공시설 운영·개방 참고 데이터를 보관합니다. 추천 시점의 운영 공지 확인은 공개 홈페이지 크롤링으로 별도 보완합니다.

**AI 운동 코치**

- `m3_processed.culture_fitness_measurement_prescriptions` — 처방 문구 키워드로 검색합니다. 연령대·성별·측정 장소는 조회 결과에 포함된 자료입니다.
- `m3_processed.culture_location_fitness_measurement_prescriptions` — 처방 문구 키워드와 프로필 지역(있을 때)으로 검색합니다. 연령대·체력 측정값·측정센터는 조회 결과의 근거 정보입니다.

**분석·운영 기록**

- `m3_derived.facility_recommendation` — 시설 추천용 파생 결과를 보관합니다. 현재 추천 요청은 최신 조건으로 점수를 다시 계산합니다.
- `m3_monitoring.pipeline_run_history` — `run_id`, 단계별 처리 건수, 상태와 오류를 기록해 파이프라인·DQ 실행을 모니터링합니다.

Supabase DB 전체 적재 현황은 다음과 같습니다. 행 수는 README에 기록된 테이블별 `COUNT(*)` 조회 스냅샷이며, 실시간 값이 아닙니다.

| 스키마 | 테이블 수 | 스냅샷 행 수 합계 |
|---|---:|---:|
| `m3_raw` | 19 | 2,511,493 |
| `m3_processed` | 18 | 2,369,349 |
| `m3_derived` | 1 | 113,852 |
| `m3_monitoring` | 1 | 86 |
| **합계** | **39** | **4,994,780** |

> `m3_raw`와 `m3_processed`는 같은 원천 데이터의 수집본·정제본을 각각 보관할 수 있습니다. 따라서 전체 행 수 합계는 테이블에 저장된 행의 합이며, 중복을 제거한 고유 데이터 수가 아닙니다. 실제 사용자 흐름에서 직접 조회하는 것은 시설·날씨·대기질, AED·안전점검, AI 운동처방 데이터입니다.

## 7. 주요 프로시저

> **프로시저** — 서비스 안에서 일이 처리되는 **순서**입니다. 요리 레시피처럼 "무엇을 먼저 하고 다음에 무엇을 하는지"를 정리했습니다.

### 7-1. 추천 점수 계산

#### 추천은 이런 순서로 만들어집니다

![우심운까 운동 장소 추천 과정](docs/images/recommendation-flow.png)

#### 점수 공식

```text
기본 점수 (45)
+ 거리 점수 (최대 40)
+ 날씨·대기질 보정
- 운영정보 감점
= 최종 추천 점수 (0 ~ 99점)
```

| 조건 | 점수 | 이유 |
|---|---:|---|
| 기본 점수 | 45 | 모든 후보의 출발점 |
| 거리 | `40 − 거리(km) × 18` (최소 0) | 가까울수록 높음 (1km → +22, 2km → +4) |
| 비 · 실내 시설 | **+8** | 비 오는 날엔 실내가 좋음 |
| 비 · 실외 시설 | **−24** | 비 오는 날 야외 운동은 어려움 |
| 실외 · 기온 10~25℃ | +6 | 야외 운동하기 좋은 날씨 |
| 실외 · 기온 5℃ 미만 또는 30℃ 초과 | −10 | 너무 춥거나 더움 |
| 실외 · 습도 40~70% | +4 | 쾌적함 |
| 실외 · 습도 80% 이상 | −8 | 너무 습함 |
| 실외 · 풍속 8m/s 이상 | −8 | 바람이 강함 |
| 미세먼지 나쁨 (PM10 ≥ 81 또는 PM2.5 ≥ 36) · 실내 | **+14** | 공기가 나쁘면 실내로 |
| 대기질 양호 · 실외 | +5 | 밖에서 운동해도 괜찮음 |
| 운영 공지에 "오늘 휴무 · 금일 휴무 · 오늘 휴관 · 임시 휴관" | **−25** | 헛걸음 방지 |

#### 같은 거리, 다른 날씨 — 계산 예시

두 시설 모두 **1km** 거리이고, **비가 오고 미세먼지가 나쁜** 날이라고 가정합니다.

| 항목 | 🏋️ 실내 헬스장 | 🏞️ 공원 운동장 |
|---|---:|---:|
| 기본 점수 | 45 | 45 |
| 거리 점수 (40 − 1 × 18) | +22 | +22 |
| 비 보정 | +8 | −24 |
| 미세먼지 나쁨 → 실내 가점 | +14 | 0 |
| **합계** | **89점** 🥇 | **43점** |

>

### 7-2. 데이터 파이프라인

> **데이터 파이프라인** — 수도관을 따라 물이 흐르듯, 데이터가 여러 처리 단계를 거쳐 흐르는 구조입니다. 이 프로젝트에서는 수집 → 원천 데이터 적재 → 정제·품질검사(DQ) → 정제 데이터 적재 과정을 자동화했습니다.

![우심운까 데이터 파이프라인](docs/images/data-pipeline.png)

| 단계 | 하는 일 | 예시 |
|---|---|---|
| 수집 | 시설·기상·대기질 API 호출 | API별 오류·재시도 정책을 적용하고 최종 상태를 기록 |
| 원본 보존 (RAW) | 받은 응답을 손대지 않고 저장 | 나중에 "원래 값이 뭐였지?"를 확인할 수 있음 |
| 정제 (Cleaning) | 제각각인 필드를 표준 컬럼으로 통일 | `faci_nm` → `facility_name`, 문자열 좌표 → 숫자 |
| 품질검증 (DQ) | 필수값 누락·중복·좌표 범위 검사 | 좌표 (0, 0)·범위 밖 값은 통과시키지 않음 |
| 적재 (PROCESSED) | 정상 데이터와 품질 확인 필요 데이터를 구분해 저장 | 제외 기준에 해당한 행은 적재하지 않고, 확인 필요 행은 표시를 남겨 보존 |
| 로그 | 실행 번호·건수·상태·오류 기록 | 어느 단계에서 몇 건이 빠졌는지 추적 |

정기 파이프라인은 데이터셋별 주기로 수집·정제·DQ·적재를 수행합니다. 실행 이력은 `m3_monitoring.pipeline_run_history`와 로그에 남기고, 실패·이상은 Discord로 알립니다. 추천 시점의 운영·휴무 공지는 배치 적재와 별개로 크롤링하며 해당 요청의 후보 재정렬에만 반영합니다.

![한 번이 아니라, 반복해서 처리되는 구조](docs/images/slides/05-pipeline.png)

#### 정기 적재와 추천 시점 크롤링은 별도 작업입니다

| 처리 | 실행 시점 | 저장·활용 |
|---|---|---|
| 공공·문화 데이터 파이프라인 | 데이터셋별 스케줄 | `m3_raw` → 정제·DQ → `m3_processed`; 이력은 `m3_monitoring` |
| 시설 운영 공지 크롤링 | 사용자가 추천을 요청할 때 | 공개 페이지 문구를 해당 요청에만 반영해 후보 재정렬 |

### 7-3. 크롤링 (운영·휴무 정보 확인)

> **크롤링** — 사람이 웹페이지를 열어 읽듯, 프로그램이 공개된 웹페이지의 글자를 자동으로 읽어 오는 것입니다.

시설 기본정보만으로는 추천 시점의 **휴무·휴관·임시 운영중단** 여부를 알기 어렵습니다. "오늘 임시 휴관" 같은 최신 공지는 공공데이터에 없기 때문입니다.
그래서 **사용자가 추천을 요청하는 순간**, 상위 후보 시설의 공개 홈페이지에서 다음 문구를 찾습니다.

`휴관` · `휴무` · `운영시간` · `공사` · `점검` · `임시` · `이용 제한` · `폐관` · `예약`

![우심운까 시설 운영정보 확인 과정](docs/images/crawling-sequence.png)

| 결과 상태 | 의미 | 화면 표시 |
|---|---|---|
| `ok` | 공지 문구를 찾음 | 추천 카드에 운영 공지 표시 |
| `no_homepage` / `no_public_page` | 공개 페이지가 없음 | 확인 필요 |
| `blocked_by_robots` | 사이트가 자동 접근을 허용하지 않음 | 접근하지 않고 확인 필요 |
| `request_failed` / `crawl_failed` | 페이지 요청 실패 | 시설은 유지, 확인 필요 |

> - 5개 시설을 **동시에** 확인해 기다리는 시간을 줄였습니다.
> - 크롤링 결과는 **그 요청에만 사용하고 DB에 저장하지 않습니다.**
> - 문구 추출 방식이라 "영업 여부를 완벽하게 판별"하기보다 **"공지를 확인해 헛걸음 가능성을 줄인다"** 가 정확한 설명입니다.

![오늘 문 열었나?는 API에 없어서 직접 확인합니다](docs/images/slides/06-crawling.png)

### 7-4. 예외 처리

> 데이터가 없거나 틀렸을 때 **서비스가 멈추지 않도록**, 그리고 **없는 정보를 지어내지 않도록** 미리 기준을 정했습니다.

| 예외 상황 | 처리 방법 |
|---|---|
| 데이터 수집 API 요청 실패 | 파이프라인 재시도 정책에 따라 재시도하고, 최종 실패는 실행 이력·로그에 기록 |
| JSON이 아닌 응답 | 오류 응답과 URL을 실행 로그에 기록하고 해당 작업 실패로 처리 |
| API 키 누락 | 환경변수 오류 안내 |
| DB 시설 후보 없음 | 카카오 로컬 장소 검색 결과를 보완 후보로 사용; 기본 DB 추천과 다른 간소화 점수식이며 환경 점수는 동일하게 적용되지 않음 |
| 추천 시 날씨·대기질 자료가 없음 | 확보된 조건으로만 점수를 계산하고 누락 환경값은 보정에 사용하지 않음 |
| 좌표 누락 | 거리 계산 제외 또는 후순위 처리 (이동시간 `확인 필요`) |
| 잘못된 좌표 (범위 밖·500km 초과) | 적재 전 오류 데이터로 분리, 추천 후보에서 제외 |
| 위치 권한 거부 | 선택한 지역의 중심 좌표로 대체 |
| 홈페이지 없음 | `no_homepage` 기록 |
| robots.txt 차단 | 크롤링 중단 |
| 운영 페이지 요청 실패 | `request_failed` 기록 |
| 처방 DB 검색 실패 | 조회 실패 상태를 기록하고 처방 근거를 확인한 것처럼 답하지 않음 |
| AI API 실패 | 오류를 사용자에게 안내; 추천·처방 DB 조회와 AI 답변 생성은 별도 단계 |
| AI 운동처방 검색 결과 없음 | `no_matching_prescription` 상태를 답변 context에 전달하며 검색 조건을 자동 완화하지 않음 |
| AI 운동처방 일부만 일치 | 138만 건 전체가 아니라 테이블별 최대 50건을 검색·집계하고 신뢰도(`high`·`medium`·`low`)를 함께 전달 |
| 체력·컨디션 위험 신호 | 처방 데이터를 근거로 운동을 권하지 않고 운동 중단·전문가 상담을 안내 |
| 프로필·컨디션 정보 부족 | 입력되지 않은 연령·성별·측정값은 임의로 채우지 않고 제공된 질문·프로필 범위 안에서 안내 |

> 확인되지 않은 데이터를 임의로 만들지 않고 `NULL`, `확인 필요`, `데이터 없음`으로 구분합니다.

### 7-5. AI 운동 코치 '우심이'

'우심이'는 기존 챗봇 안에서 동작하는 AI 운동 코치입니다. 시설 추천처럼 새로운 카테고리를 따로 만들지 않고, 사용자가 챗봇에 컨디션이나 운동 방법을 질문하면 **운동처방 데이터와 회원 context를 근거로 오늘의 운동을 제안**합니다.

![AI 운동 코치 우심이 화면](docs/images/ai-coach-usimi.png)

| 우심이가 참고하는 정보 | 예시 |
|---|---|
| 프로필의 지역·선호 운동 등 챗봇 context | 저장된 값이 있을 때 질문 해석과 시설 추천에 참고 |
| 최근 운동 기록 (최근 5건) · 누적 칼로리 · 레벨 | 3,200kcal · LV.12 |
| 추천 시설 상위 3곳 · 점수 · 추천 이유 · 운영 공지 | "비가 와서 실내 시설 우선" |
| 날씨 · 대기질 수치 | 기온 18℃, PM10 45 |
| `m3_processed.culture_fitness_measurement_prescriptions` | 25,070건: 연령대·성별·측정 장소별 운동처방 |
| `m3_processed.culture_location_fitness_measurement_prescriptions` | 1,389,228건: 지역·연령대·체력 측정값·측정센터·운동처방 |

#### 운동처방 데이터가 답변으로 바뀌는 과정

예를 들어 사용자가 “오늘 컨디션은 보통이고 20분 정도 가능해. 맨몸운동 추천해줘”라고 입력하면 다음 순서로 처리합니다.

1. Django가 질문 의도를 확인하고, 운동처방 질문이면 검색 키워드를 추출합니다.
2. 두 운동처방 테이블에서 처방 문구를 SQL `ILIKE`로 검색합니다. 위치기반 테이블은 프로필 지역이 있을 때 시·도·시군구 조건도 적용합니다. 연령·성별·체력 측정값은 검색 필터가 아니라 조회된 처방 행의 메타데이터입니다.
3. 138만 건 전체를 OpenAI에 보내지 않고, DB에서 조건에 맞는 후보를 최대 50건씩 가져옵니다. 같은 처방이 반복되면 묶어서 빈도와 공통 운동 키워드를 계산합니다.
4. `matched_count`, 고유 처방 수, 공통 운동, 신뢰도(`high`·`medium`·`low`)와 대표 처방 일부만 AI에 전달합니다.
5. AI는 전달된 처방 근거와 질문·최근 운동 기록을 참고해 운동, 이유, 주의사항을 자연어로 답합니다. 의학적 평가나 개인별 처방 효과를 확정하는 기능은 아닙니다.

즉, AI가 138만 건을 암기하거나 임의로 운동을 만드는 방식이 아니라 **DB에서 먼저 키워드와 가능한 지역 조건으로 후보를 좁히고, 집계된 근거를 바탕으로 자연어 답변을 생성하는 구조**입니다. 시설의 추천 순서는 여전히 거리·날씨·대기질·운영 공지를 이용한 규칙 기반 점수 계산으로 결정되며, AI는 그 결과를 설명하거나 운동 방법을 안내합니다.

#### 일부 검색 결과에서 문제가 생길 때의 기준

| 상황 | 처리 결과 |
|---|---|
| 검색 결과가 없음 | `no_matching_prescription`으로 기록하고 일치 자료가 없음을 명시; 데이터 기반 처방인 것처럼 꾸며내지 않음 |
| 일치 데이터가 너무 적음 | `low` 신뢰도로 표시하고 특정 처방을 확정적으로 말하지 않음 |
| 여러 처방이 조회됨 | 반복 처방을 집계해 대표 근거를 전달하되, 개인별 확정 진단처럼 표현하지 않음 |
| 통증·부상·호흡곤란·흉통 등 위험 신호 | 운동 추천을 중단하고 즉시 휴식 및 의료 전문가 상담 안내 |
| DB 조회 또는 AI API 실패 | 실패 상태를 구분해 안내하고, 확인하지 못한 자료를 조회한 것처럼 표현하지 않음 |

![우심이 데이터 기반 챗봇 응답 과정](docs/images/chatbot-sequence.png)

**우심이의 규칙**

- 항상 한국어 존댓말로, 짧고 친근하게 답합니다.
- 제공된 추천 데이터를 **가장 우선**하고, 모르는 실시간 날씨·운영 여부를 **아는 척하지 않습니다.**
- 통증·호흡곤란·흉통 같은 위험 신호가 나오면 **운동 중단과 의료 전문가 상담**을 안내합니다.
- 극단적인 다이어트 방법을 권하지 않습니다.
- **OpenAI API 키는 서버에만 있고**, 브라우저에는 절대 전달되지 않습니다.

#### 파이프라인 처리 결과 — 별도 실행 스냅샷

아래 표는 18개 데이터셋의 **한 파이프라인 실행 집계**입니다. DB 전체 `COUNT(*)` 스냅샷과는 측정 시점·집계 범위가 다르므로 두 합계를 같은 값으로 취급하면 안 됩니다. 실행 집계는 **2,445,724건 수집 = 2,367,256건 정제·적재 + 78,468건 제외**이며, 적재분 중 **135,920건(5.7%)**은 삭제하지 않고 품질 확인 대상으로 표시했습니다.

**수치 차이의 정리:** DB 전체 스냅샷의 `m3_processed`는 **2,369,349행**으로, 위 실행의 적재 합계보다 **2,093행 많습니다**. `m3_raw` 전체는 **2,511,493행**으로 실행 수집 합계보다 **65,769행 많습니다**. 이는 서로 다른 집계(테이블의 스냅샷 행 수 vs 단일 실행의 입력·출력 건수)라서 차이를 임의로 더하거나 빼지 않았습니다. 이 저장소에는 해당 DB 스냅샷의 쿼리 출력과 파이프라인 실행 원본 로그가 포함돼 있지 않아, 차이의 세부 원인이나 이후 변경분은 여기서 재검증할 수 없습니다.

![18개 데이터셋 수집·정제·품질검증 결과](docs/images/pipeline-results.png)

> **"제외"와 "품질 확인 필요"는 다릅니다.**
> - **제외** — 중복이거나 필수 정보가 없어 쓸 수 없는 행. 정제 단계에서 빠지고 적재되지 않습니다.
> - **품질 확인 필요** — 쓸 수는 있지만 일부 값(예: 좌표, 측정값)이 비었거나 의심스러운 행. **지우지 않고 표시만** 해 두어, 나중에 확인·보완할 수 있게 했습니다.
>
> **실행 내 건수 검산:** 2,445,724(수집) = 2,367,256(정제·적재) + 78,468(제외). 표의 18개 데이터셋 합계 안에서는 일치합니다. 이는 한 실행의 산술 검산이며, 현재 DB 스냅샷과 동일하다는 뜻은 아닙니다.

## 📖 용어 사전

| 용어 | 쉬운 설명 |
|---|---|
| **API** | 프로그램끼리 정보를 주고받는 창구. "기상청아, 지금 관악구 날씨 알려줘" 같은 요청을 보내는 곳 |
| **공공데이터** | 정부·공공기관이 누구나 쓸 수 있도록 공개한 데이터 (체육시설 목록, 날씨, 미세먼지 등) |
| **프론트엔드** | 사용자가 보는 화면 부분 |
| **백엔드** | 화면 뒤에서 계산·저장을 담당하는 서버 부분 |
| **Django** | 파이썬으로 웹 서비스의 백엔드를 만드는 도구 |
| **Supabase** | PostgreSQL 데이터베이스·API 등을 관리형으로 제공하는 서비스. 이 프로젝트의 운영 데이터베이스 |
| **PostgreSQL** | Supabase가 데이터를 표 형태로 저장하는 관계형 데이터베이스 엔진 |
| **PostGIS** | Supabase PostgreSQL에 설치해 좌표·거리 등 공간 데이터를 처리하는 확장 기능 |
| **좌표 (위도·경도)** | 지구 위의 위치를 숫자로 나타낸 것 (예: 37.59, 127.09) |
| **RAW / PROCESSED** | RAW = 받은 그대로의 원본, PROCESSED = 깨끗하게 정리한 데이터 |
| **전처리 (Cleaning)** | 제각각인 이름·형식을 통일하고 잘못된 값을 정리하는 작업 |
| **품질검증 (DQ, Data Quality)** | 빠진 값·중복·말이 안 되는 값이 없는지 검사하는 작업 |
| **파이프라인** | 수집 → 정제 → 검증 → 저장을 자동으로 이어 붙인 흐름 |
| **크롤링** | 프로그램이 공개 웹페이지의 내용을 자동으로 읽어 오는 것 |
| **robots.txt** | 웹사이트가 "자동 프로그램은 여기까지만 들어와 주세요"라고 적어 둔 안내문 |
| **규칙 기반 추천** | 사람이 정한 기준(점수표)으로 순위를 매기는 방식. AI 학습 없이도 이유를 설명할 수 있음 |
| **ERD** | 데이터베이스 표들과 그 관계를 그린 설계도 |
| **환경변수** | 비밀번호·API 키처럼 코드에 직접 쓰면 안 되는 값을 서버에 따로 보관하는 방법 |
| **해시 (Hash)** | 비밀번호를 원래대로 되돌릴 수 없는 값으로 바꿔 저장하는 방식 |
| **배포 (Render)** | 내 컴퓨터에서만 돌던 서비스를 인터넷 서버에 올려 누구나 접속하게 하는 것 |
| **OpenAI API** | ChatGPT를 만든 회사의 AI를 우리 서비스 안에서 쓸 수 있게 해 주는 창구 |
